# D45：重驗驗收線 7（fps）— 設計

- 日期：2026-08-04
- 對應債務：`docs/specs/2026-07-29-project-review.md` D45
- 對應驗收線：`docs/specs/2026-07-26-p1e-fullscreen-audio-design.md` §8 第 7 條

## 0. 這份文件解決什麼

驗收線 7「fps 不回歸：`MIRAGE_FPS_LOG` 在全螢幕串流解析度上限下 **≥ 55**」目前在
`RESULTS-p1e.md` 仍掛著 `pending-human`，理由是「headless／螢幕關閉下 `.task` 未被驅動」。

**那個理由早已失效，而且這件事在 2026-07-29 就寫進程式碼註解了**——
`app/Sources/MirageCore/Viewport/StreamSize.swift` 的 doc comment 白紙黑字寫著：

> **驗收線 7 的 pending 歸因是錯的**。它不是「需解鎖螢幕」——鏡像顯示當時根本沒在運作
> （`AVAudioEngine` 的 NSException 打死 MainActor），與螢幕鎖定無關。防護已在樹上，
> **該驗收線現在量得了**。

從那天到今天，沒有人回頭量。D32 重驗了驗收線 6（同一個失效理由），並在收尾時把驗收線 7
記成 D45——**因為沒有編號的東西每一輪都會被合理地跳過**（D33 那列自己寫下的教訓）。

本文件是那次重驗的設計。

## 1. 已知事實（重驗前就有的資料）

**這些數字全部已經存在**，D45 不是從零開始量，而是補上缺的那一格並據以判定。

### 1.1 不經過 Mirage 的對照組也只有 30.4 fps

`docs/specs/2026-07-28-mirror-never-rendered-investigation.md` §11.1 用 Python harness
直接量同一條串流（**完全不經過 Mirage**）：

```
fps=30.4  p50=28.8ms  p95=78.2ms  avg_frame=2.47MiB  throughput=75MiB/s  (540x1200)
```

同時間 Mirage 側是 20–35 fps。**兩者一致 → Mirage 的顯示路徑沒有額外損失。**

### 1.2 解析度掃描：任何一格都遠低於 55

同檔 §11.2，同機同內容：

| 解析度 | 像素 | fps | p50 | p95 | 吞吐 |
|---|---|---|---|---|---|
| 270×600 | 0.16 MP | 32.3 | 22.0ms | 72.0ms | 20 MiB/s |
| 540×1200 | 0.65 MP | 30.4 | 28.8ms | 78.2ms | 75 MiB/s |
| 1080×2400 | 2.59 MP | 22.0 | 37.2ms | 101.7ms | 218 MiB/s |

解析度降到 1/4，fps 只從 30.4 升到 32.3——不是頻寬瓶頸的形狀。§11.2 據此**推論**瓶頸在
guest 端的畫面產生速率，但同一段明確標記：

> ⚠️ 這條推論**尚未直接量到 guest 端的 render fps**。試過 `dumpsys SurfaceFlinger
> --latency`（這版 Android 拿不到資料）與 `getevent`（時序不可靠）。**在那之前這是推論，
> 不是結論。**

### 1.3 D32 順手量到的 `MIRAGE_FPS_LOG`：34–46，但不可用

D32（2026-08-03）五次 60 秒量測得到 `FPS_AVG` 34／46／45／34／37。**這批數字不能拿來判
驗收線 7**，兩個理由：

1. **視窗模式，非全螢幕**
2. **串流尺寸一路變動**（同一次量測內出現 540×1200、888×1972、900×2000），fps 是混合的

### 1.4 缺的那一格

`StreamSize` 的實際上限是 `maxPixels = 1_800_000`（1.8 MP），不是 `maxWidth = 1080`。
9:20 直向 guest 在全螢幕下算出 **900×2000 = 1.8 MP**。

而 §11.2 的三個量測點是 0.16／0.65／2.59 MP——**1.8 MP 這一格沒有任何量測資料**，
`StreamSize.swift` 的註解自己也標了這件事（「要調整它得先補量」）。

**這就是 D45 要補的量測點。**

## 2. 決策

| # | 決策 | 理由 |
|---|---|---|
| 1 | 在**真全螢幕**下量，並**斷言串流尺寸為 900×2000** | 驗收線 7 字面要求「全螢幕串流解析度上限下」。D32 的失敗正是尺寸沒收斂就開始計時 |
| 2 | **同一輪一併量對照組**（`bench_mmap_vs_rgba.py` 的 rgba 路徑），但兩者**先後跑、不並行** | 新判準要對著對照組，所以必須是同一輪、同一環境下的數字；但並行跑會有兩個 client 搶同一條串流、互相干擾 |
| 3 | 對照組工具用 **venv** 修，不動系統 protobuf | 見 §4。系統上還有別的東西吃 protobuf 4.25，升級是外溢的改動 |
| 4 | 限時試坐實瓶頸，**最多三個方法** | 坐實與判準重新表述**互相獨立**（見 §6），試不出來不阻塞主線 |
| 5 | 若不通過就**重新表述判準**，並在 spec 加更正註記 | 比照驗收線 6（D32）的處理。留著一個結構上達不到的判準，下一輪還是會困惑 |

## 3. 量測設計

兩個數字，同一個遊戲畫面狀態下**先後**量：

| | 工具 | 條件 |
|---|---|---|
| Mirage 側 | `MIRAGE_FPS_LOG`（經 `app/scripts/lib/gui_session.sh`） | 全螢幕，串流尺寸斷言 900×2000 |
| 對照組 | `phase0/harness/bench_mmap_vs_rgba.py`（rgba 路徑） | 同樣請求 900×2000，不經過 Mirage |

### 3.1 全螢幕怎麼進、怎麼確認真的進去了

全螢幕的產品入口是選單列項目（`AppModel+FullScreen.swift`：
`NSApp.keyWindow?.toggleFullScreen(nil)`），對應快捷鍵 ⌃⌘F。自動化用 `osascript` 送鍵，
沿用 D32 已驗證的 `osascript` 拉前景手法。

**不可假設它成功了。** 判斷依據是串流尺寸——全螢幕會讓 `resizeDebounced` 重算內容矩形寬
（螢幕高 × aspect），經 `StreamSize` clamp 到 `maxPixels`。本機螢幕 2560×1600 Retina，
9:20 直向 guest 算出 900×2000。**腳本必須先等到 log 裡出現 900×2000 才開始計時**，
等不到就中止並報告——那代表全螢幕沒進去，或這台螢幕不夠大。

### 3.2 §11.3 的三個陷阱，全部照做

1. **guest 畫面必須持續變化**——`streamScreenshot` 是變化驅動的。拿 launcher 或靜止的
   遊戲畫面量到的是「靜止期」，不是效能。
2. **必須 release build**——debug 慢 3–4 倍。
3. **不能拿 launcher 當對照組**——§11.3 自己踩過，量到 12.7 fps 那次量的是 swipe 之間的
   靜止期。

### 3.3 為什麼兩者先後跑而不並行

兩個 client 並行拉同一條 `streamScreenshot` 會互相干擾，量到的是「兩個消費者下的幀率」，
不是任一方的能力。代價是兩次量測的遊戲畫面內容不完全相同——用「關卡內持續動作」的畫面
狀態、各量 60 秒、跑多次取分佈來吸收這個變異。

## 4. 前提障礙：對照組工具目前是死的

`phase0/harness/` 底下 **11 個檔案** import `gen/emulator_controller_pb2.py`，而該產生碼
標記 `Protobuf Python Version: 7.35.0`、開頭就呼叫 `_runtime_version.ValidateProtobufRuntimeVersion`。
本機裝的是 **protobuf 4.25.4**，`import` 直接炸：

```
ImportError: cannot import name 'runtime_version' from 'google.protobuf'
```

`tools/probe/probe.py` 也走同一條路，同樣跑不起來。

**修法：建立 venv，在裡面裝相容版本的 protobuf 與 grpcio，只給 D45 的對照組量測用。**
不升級系統 protobuf——這台機器上還有別的東西依賴 4.25，升級的影響面遠超 D45。

⚠️ **「`phase0/harness` 整批是死的」本身是一筆債**（與 D37「`tools/probe/tests` 的 13 個
檔從未被跑過」同型），但**不在 D45 裡修**。D45 只負責讓對照組跑得起來，並把這個發現記成
新債務。

## 5. 限時試坐實瓶頸

依序試，**試到第一個給得出可用數字的為止，最多三個**。「可用」的判準是：那個數字必須真的
對應到 Pixel Flow 的出幀速率——例如 `gfxinfo` 若回了資料但那是系統 UI 的幀、不含 Unity
自繪的 SurfaceView，就不算數，要往下一個方法試。

| # | 方法 | 已知風險 |
|---|---|---|
| 1 | `dumpsys gfxinfo <pkg> framestats` | Unity 走 SurfaceView 自繪，可能整個不被計入——先驗有沒有資料再往下 |
| 2 | `dumpsys SurfaceFlinger --timestats` | 與已知失敗的 `--latency` 是不同子系統，TimeStats 有 fps histogram |
| 3 | emulator 自己的 gRPC 是否暴露統計 | 未查證過有沒有這種 API |

**試不出來就如實寫「仍是推論」**，不用間接數字硬湊成結論。§11.2 自己從 2026-07-28 起就
誠實標著這條限制，D45 不該為了讓報告好看而降低那個標準。

## 6. 判準重新表述

### 6.1 為什麼 `≥ 55` 衡量錯了東西

驗收線 7 的標題是「**fps 不回歸**」——不回歸本來就是相對概念。是後面那個 `≥ 55` 把它偷換
成絕對值。

而 §11.1 已經證明：不經過 Mirage 的對照組也只有 30.4，兩者一致。**這個絕對數字衡量的是這台
模擬器產生畫面的能力，不是 Mirage 的效能。** Mirage 沒有任何辦法讓它變成 55。

### 6.2 新表述

**`MIRAGE_FPS_LOG` 的平均不低於同條件對照組的 N%。**

`N` 由實測決定，**不從理論推導**（D32 的教訓：先定門檻再實測，會定出結構上不可能成立的
判準）。

絕對 fps 仍如實記載在 RESULTS 裡，只是不當通過判準。

### 6.3 這個表述與「坐實瓶頸」互相獨立

「不低於對照組」**不需要知道 guest 的 render fps 是多少**。§5 的坐實工作是為了解釋「為什麼
只有 30」，不是新判準的前提。兩者不綁在一起——坐實失敗，判準照樣能改。

## 7. 不在本次範圍

- **修 `phase0/harness` 的 protobuf 問題本身**：D45 用 venv 繞過，讓對照組跑得起來即可。
  「11 個 harness 檔案全是死的」記成新債務。
- **調整 `StreamSize.maxPixels`**：1.8 MP 這個值補上量測點之後，可能顯示它訂得不合適。
  但改上限會影響所有既有的 fps／延遲數字的可比性，該是獨立決策。本次只補量測點。
- **D47（`verify_audio_gui.sh` 的 A4 fps 門檻 `≥ 27`）**：它同樣是絕對值，D45 若重新表述了
  驗收線 7，這條可能要跟著調。**本次不順手改**，只在 D47 記一句「等 D45 的結論」。
- **提升 fps 本身**：若坐實瓶頸在 guest 端，那是模擬器／遊戲的事，不是 Mirage 能解的。
  真要處理需另開設計。
