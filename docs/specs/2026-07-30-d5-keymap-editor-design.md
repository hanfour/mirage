# D5：keymap 編輯器設計

2026-07-30。對應債務 **D5**（overlay 編輯器不能拖），連帶關閉 **D22**（編輯模式擋鍵盤沒擋滑鼠）
與 **D12**（搖桿觸點沒有 clamp）。

---

## 1. 問題不是「編輯器不能拖」

D5 記載的是「29 行、只有存檔按鈕、不能拖曳」。那是**症狀**。查證後真正的缺口更前面：

**目前沒有任何路徑能讓使用者為正在玩的遊戲取得鍵位。**

- 唯一的內建 profile 是 `com.example.game`——一個**沒有任何真實遊戲會用的佔位 gameId**
  （`Sources/MirageCore/Resources/profiles/com.example.game.json`）。
- `AppModel.toggleEditing()` 的 guard 是 `guard editing || profile != nil`，而 `profile` 來自
  `applyActivation()` 的 `store.load(gameId: currentPackage)`。玩真實遊戲時載不到檔 → `profile` 為 nil
  → **⌘E 完全沒有反應**。
- 逃生路徑也不通：選單列「套用 profile ▸」可以強制套用 `com.example.game` 的版面，但
  `saveProfile` 存回 `p.gameId`、`bumpVersion` 保留原 gameId，所以編輯後**存回那個佔位檔**，
  不會為當前遊戲建立任何東西。

因此本設計的範圍是**完整編寫器**：建立 profile → 新增／刪除 binding → 指定按鍵 → 拖曳調整
→ 存檔。只做 D5 字面範圍（拖曳／半徑／靈敏度）的話，做完之後真實遊戲的使用者按 ⌘E
仍然沒有反應。

> **這一段本身就是本專案 §0 誤診模式的又一個實例**：債務條目描述的是看得見的症狀，
> 而擋住使用者的是它前面那一步。動手前先走一次完整使用者旅程，才會發現第 3 步做完
> 沒有用，因為第 1 步不存在。

## 2. 已定的四個決定

| 決定 | 選擇 | 理由 |
|---|---|---|
| 範圍 | **完整編寫器** | 見 §1。只補拖曳，編輯器仍然打不開。 |
| 版面 | **底部抽屜** | 見 §3。 |
| 起點 | **預填 starter 版面** | 第一眼不是空白畫面；多數人是微調而不是從零建。 |
| 存檔 | **即時套用＋明確存檔** | 拖拉即時反映在 overlay，只有按「存檔」才寫檔（version+1）；⌘E 離開時若有未存變更，跳「存檔／捨棄／繼續編輯」。 |

### starter 版面的來源與落檔時機（消除歧義）

- **來源**：複製內建 profile 的 `bindings`，套上**當前遊戲的 gameId**、`version: 1`。
  只借版面，不借 gameId——借了 gameId 就會存回那個佔位檔，正是 §1 描述的死路。
- **內建 profile 讀不到時**（bundle 壞掉，見 D25）：退回一份**寫死在碼裡**的 starter
  （搖桿 WASD ＋ 兩顆點擊鍵 ＋ 視角）。編輯器不該因為資源問題而完全打不開。
- **落檔時機**：⌘E 只在**記憶體**裡建出 starter profile，**不寫檔**。檔案要到按下「存檔」
  才出現。這是「明確存檔」語意的直接推論——否則不小心按到 ⌘E 就會憑空生出一個檔案。

### 為什麼是底部抽屜，不是側欄或純直接操作

- Mirage 的視窗是**手機比例**（9:20 直向、最小寬 270pt）。側欄會吃掉超過一半寬度，
  鏡像被壓窄後「所見即所得」失真，拖出來的位置不準。**吃高度比吃寬度便宜。**
- **`.look`（視角／靈敏度）在畫面上沒有任何視覺標記**——現行 `KeymapOverlay` 對 `.look`
  直接畫 `EmptyView`，而且本設計刻意維持這個行為（見 §4）。純直接操作沒有任何地方
  能碰到它。抽屜的清單是它唯一的棲身之處。
- 新增／刪除有固定位置，不必靠長按之類的隱藏手勢。

已知代價：抽屜遮住畫面下半部，而技能鍵通常就放在那裡。緩解方式是抽屜半透明，
或選中的 binding 若被遮住則暫時上移——**實作時再處理，不預先設計**。

## 3. 資料模型與既有債的相撞

以下五件事不一起處理就做不出可用的編輯器。

### 3.1 `Binding` 沒有身分 → 身分留在編輯階段

`Binding` 是裸 enum 存在 `[Binding]` 裡，`KeymapOverlay` 用 `id: \.offset`（陣列索引）識別。
編輯器要選取／刪除，索引當身分必壞：刪掉第 1 筆，第 2 筆的索引變成 1，選取跳到錯的東西上。

**決定：不動檔案格式。** 編輯器內部持有 `[(id: UUID, binding: Binding)]`，存檔時攤平回
`[Binding]`。身分是**編輯階段的概念**，不是 profile 的屬性——寫進 JSON 只會多一套版本遷移，
換不到任何東西。

### 3.2 陣列順序有語意 → 不提供拖曳排序

`KeymapEngine` 對 joystick/look 採一對一 id 模型，觸點 identifier 由順序決定
（既有測試註解：「搖桿是第一個 binding → identifier 1」）。重排會改變送給 guest 的
touch identifier。

**決定：清單顯示順序，但不提供拖曳排序。** 要支援排序就得連 `KeymapEngine` 的 id 模型
一起重新設計，那是另一輪的事。

### 3.3 `validated()` 限制最多 1 個 joystick、1 個 look

已存在的約束（`ProfileError.identifierConflict`）。**UI 必須在源頭反映**：「＋新增」在
已有搖桿時就禁用搖桿選項，而不是讓使用者加完、存檔才報錯。

### 3.4 D22 必須一起修（不是選配）

`KeymapController.hasProfile` 是 `engine != nil && !editing`，所以**一進編輯模式它就變 false**；
而 `MirrorView.Coordinator.sendMouse` 的 `guard controller?.hasProfile != true else { return }`
正是靠這個值決定要不要退回直接 tap——**編輯模式下滑鼠點擊會直接打進 guest**。
使用者在編輯器裡拖鍵位＝在遊戲畫面上亂點。

根因是兩個語意不同的判斷共用一個述詞：
- 「該不該把滑鼠交給引擎」（engine 存在與否）
- 「該不該把事件送出去」（是否在編輯模式）

**決定：拆成兩個述詞。** 編輯模式下 `Coordinator` 不送 tap，也不交給引擎。

### 3.5 D12 順手修掉

搖桿 `center ± radius` 目前可越界，`validated()` 不檢查。拖到邊緣就注入越界座標。
D7 已經確立這個立場：**送越界座標比不送更糟**——畫面有反應但點在錯的地方，
而使用者會以為是遊戲的問題。

**決定：夾取在純函式裡完成**（比照 D7 的 `NormPoint.fromViewPoint`），
並補進 `validated()`。

### 3.6 分層

座標換算、半徑夾取、profile 變換（新增／刪除／改鍵／改參數）**全部是純函式，放 `MirageCore`**。
App 層只負責手勢辨識與畫面。比照 `KeyTranslate`／`StreamSize`／`ViewportFit`／`NormPoint`
的既有慣例——而且 `MirageCore` 是覆蓋率判定段，`MirageShell` 不是。

## 4. 互動設計

### 4.1 鏡像畫面（直接操作）

- 選中的 binding 出現兩個把手：**藍點拖圓心**、**橘方塊拖半徑**（僅搖桿有橘方塊）
- 未選取的 binding 半透明；點一下即選取
- 點擊鍵只有藍點，沒有半徑

### 4.2 底部抽屜（四個狀態）

1. **清單** — 表頭 `BINDING · n` ＋ `＋新增／存檔／完成 ⌘E`；每列一個 binding
2. **選中** — 該列高亮，下方換成參數：半徑滑桿、鍵位 chips、刪除
3. **改鍵** — 點某個 chip → 變成「按下要指定的鍵…」→ 擷取下一個按鍵。
   Esc 取消擷取；**⌘ 組合不擷取**（所以 ⌘E 仍然是離開）
4. **＋新增** — 型別選單；已存在的型別禁用（§3.3）。新 binding 落在畫面正中央
   並自動選取，直接拖走

### 4.3 四個刻意的取捨

- **半徑有兩種改法**（拖橘方塊／拉滑桿），改的是**同一個值**，不是兩套設定。
  直接操作快但不精確，滑桿精確但慢。
- **視角在畫面上不畫標記**——維持現行行為。它不是螢幕上的一個點，硬畫一個圈只會
  讓人以為那裡有東西可按。它只活在抽屜清單裡。
- **不做拖曳排序**（§3.2）。
- **刪除不做二次確認**——靠「離開時提示未存變更」兜底。確認框太吵，而且刪錯只要
  不存檔就沒事。

## 5. 測試策略

比照本專案既有慣例：**純函式逐條測，App 層測到能測的那條縫為止**。

- **`MirageCore` 純函式**（主要涵蓋）：profile 變換（新增／刪除／改鍵／改半徑／改靈敏度）、
  座標與半徑夾取、`validated()` 的新約束、starter 版面的產生。
- **App 層**：比照 `MirrorMouseReleaseTests`（把 view 裝進真 NSWindow 合成滑鼠事件）
  驗拖曳把手的命中與位移；比照 `MirrorCoordinatorTests` 驗**編輯模式下不得送出任何 tap**
  （D22 的回歸哨兵）。
- **等待一律用無預算閘門**（`CountGate`／`StateRecorder`），不得引入新的 `waitUntil`
  式輪詢——見 D24。

## 6. 非目標（YAGNI）

- 拖曳排序（§3.2）
- 多個搖桿／多個 look（受 `KeymapEngine` id 模型限制，§3.3）
- 「試玩」模式（編輯中暫時套用實測）——⌘E 進出夠快，先不做
- 從別的遊戲複製 profile
- undo/redo 堆疊（「離開時提示未存變更」已覆蓋主要的資料遺失情境）
- 存檔失敗的使用者可見提示（既有 pending，與本設計正交）

## 7. 驗收條件

1. 玩一款**沒有 profile 的真實遊戲**時按 ⌘E，進入編輯器並看到 starter 版面；
   此時**磁碟上仍然沒有該遊戲的 profile 檔**（未存檔就離開不留下任何東西）。
2. 拖曳搖桿與技能鍵可改變位置，橘方塊可改變半徑，兩者即時反映在 overlay。
3. 可新增點擊鍵、刪除任一 binding、指定任一 binding 的按鍵。
4. 已有搖桿時，「＋新增」的搖桿選項為禁用。
5. **編輯模式下滑鼠點擊不會傳到 guest**（D22 回歸哨兵）。
6. 搖桿拖到邊緣時，送出的觸點座標仍在 0–1 內（D12）。
7. 按「存檔」後 profile 以當前遊戲的 gameId 寫入，version+1，引擎立即套用。
8. 有未存變更時按 ⌘E 會提示「存檔／捨棄／繼續編輯」。
9. `./scripts/ci.sh` 四道閘門全綠。

## 8. 建議分階段（spec 自審的範圍檢查結果）

這份 spec 的份量（估 1–2 週）超過單一實作計畫的舒適範圍。建議切成三段，
**每段結束時產品都是可用的**，不是做到一半才有價值：

| 階段 | 內容 | 結束時使用者拿到什麼 |
|---|---|---|
| **A** | 建立路徑 ＋ D22 ＋ D12 ＋ 純函式層 | 真實遊戲按 ⌘E 打得開，看得到 starter 版面，編輯時滑鼠不會打進 guest |
| **B** | 底部抽屜 ＋ 拖曳 ＋ 半徑／靈敏度 | 能把 starter 版面調到自己要的位置並存檔——**D5 字面範圍到此完成** |
| **C** | 新增／刪除 ＋ 按鍵擷取 | 完整編寫器 |

刻意把 D22 排在 A：拖曳一上線就會踩到它，晚修等於一路在髒環境上開發。
