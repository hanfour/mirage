## ⚠️ 重要限制：三次都只量到 1 輪，不是 brief 預期的 3 輪中位數

**這是本次探測最需要交代的事**：`-r 3` 要求 3 輪，但這台開發機在本次量測期間 load
average 持續在 8–18 之間劇烈波動（遠超 `LOAD_LIMIT=8`），且個別輪次的**全螢幕收斂本身**
（`⌃⌘F` → 900×2000）也有不低的失敗率——即使在 load average 低於門檻時，仍有相當比例的
輪次卡在 888×1972（"最大化但非全螢幕"）而不是真正的全螢幕 900×2000，`SIZE_OK` 因此被
拖成 0，整批作廢。

**上面三次數字，每次都只有第 1 輪同時滿足「跑到」且「全螢幕收斂」，第 2、3 輪都被
`load_gate` 攔下（跳過，不是失敗）。** 三個數字因此各自只是「1 輪」而非「3 輪取中位數」
——比 brief 原意設計的抗噪能力弱，但**沒有被污染**：`SIZE_OK=1` 保證這 3 個數字量的都是
900×2000 下的真實 fps，不是別的解析度混進來的髒值。

### 重試記錄

本 task 對 `verify_fps_fullscreen.sh -r 3 -d 20`（含 Step 3 的 `-r 1 -d 20`）的呼叫，
連同被 `load_gate` 整批攔下（`ROUNDS=0`）與全螢幕未收斂（`SIZE_OK=0`）而作廢的嘗試，
**總計超過 30 次**才湊齊上面 3 筆可信數字。觀察到兩種獨立的失敗模式：

1. **`load_gate` 整批攔下**：load average 持續高於 8（一度衝到 17.95），這段時間內
   `ROUNDS=0`，全部重試。
2. **全螢幕收斂失敗（`SIZE_OK=0`）**：即使 load average 低於門檻，`⌃⌘F` 之後量到的
   仍常是 888×1972 而非 900×2000——`sleep 5` 沒能穩定等到 `resizeDebounced` 收斂，
   懷疑與這台共用機器上有其他並行的人機互動（focus 被搶走）有關，但未能確診根因。
   這個失敗模式**與 CPU 負載沒有明顯相關**：低負載窗口下同樣觀察到全 3 輪都收斂失敗
   的情況。

兩種失敗模式合計，單輪「跑到且全螢幕收斂」的成功率粗估在 3–4 成，這是為什麼湊齊
3 筆乾淨數字需要如此多次重試。**依 brief 指示直接重試，未開任何背景監控等待負載下降。**

## 結論

依這三次（每次皆 `ROUNDS=1`、`SIZE_OK=1`，僅代表單輪量測，見上方限制章節）：

- `RATIO_PCT` 三次為 91／85／90，最小值 85。依 Task 5 brief 給定的公式
  `7a 門檻 = 三次最小值 × 0.9`：`85 × 0.9 = 76.5` → **N = 76**。
- `MIRAGE_MEDIAN` 三次為 52／35／49，最小值 35。依公式
  `7b 門檻 = 三次最小值 × 0.8`：`35 × 0.8 = 28` → **M = 28**（基準常數即本次
  2026-08-04 量測，`D45_BASELINE`）。

**依這三次，7a 的 N 與 7b 的 M 建議定為 76／28。**

這組建議值是在「每次僅 1 輪」的較弱樣本下算出的，比原本設計的「每次 3 輪取中位數」
更容易被單一離群值拉動——Task 5 訂門檻時應把上方「重試記錄」與「三次都只量到 1 輪」
這件事一併納入考慮，並可自行評估是否要在較不繁忙的時段補測以取得真正的 3 輪中位數。

以上為建議值，非本 task 的斷言——`verify_fps_fullscreen.sh` 本身不含任何 `exit 1`
路徑，退出碼永遠是 0，門檻要由 Task 5 決定並加上斷言後才生效。
